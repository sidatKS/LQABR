Email Agent Log Pipeline

One event source, two renderers, two destinations. The mode switch changes how much each event carries — never which path it takes.

scope: email agent only 2026-08-26 design — not built no code changed

The pipeline

Four call sites converge on one emitter, then fan out to two sinks

Every log line in the agent already passes through _emit. Keeping it that way is what guarantees the terminal view and the stored file can never drift: they are the same event, rendered twice.

What the mode switch changes

Same events, same order — density is the only difference

Prerequisite

Three copies of configure_logging race on one logger

Configuration

VariableValuesEffect
LQABR_EMAIL_LOG_MODE normal · debug
default normal		 Logger level and field volume. Absorbs LQABR_EMAIL_LOG_MODEL_CONTENT, which is retired.
LQABR_EMAIL_LOG_DIR logs/email Created at startup. Unset means no file handler — the Cloud Run case.
LQABR_EMAIL_LOG_FORMAT console · json
default auto		 Auto-detects by TTY: console locally, JSON on Cloud Run. Override when --reload or a pipe fools the detection.
LQABR_EMAIL_LOG_MAX_FIELD_CHARS 0
0 = unlimited		 Caps long values with a (+N chars) tail. Useful on a 25-lead batch.

Validate MODE and FORMAT against their tuples and raise on anything else — the same shape as LQABR_EMAIL_ROUTES. A typo silently meaning normal is worse than a startup failure.

Build order

  1. Collapse the three configure_logging copies to one owner in outreach.py The _emit and log_* helpers stay inlined per module — only handler setup moves.
  2. configure_logging takes mode and dir; installs both handlers Rotating file handler at 10 MB × 5, ANSI stripped.
  3. Add ConsoleFormatter and the extra={"lqabr_stream": …} tag on _emit The stream name currently lives inside an opaque JSON string where no filter can see it.
  4. Add _span, _fields, _preview and the per-lead progress counter _fields walks __dataclass_fields__, so a profile field added later appears automatically.
  5. Wire spans into steps 5 through 9 Phases: load_leads, construct, send, writeback — each closing on the exception path too.

The first three are the gate — nothing is testable until they land. The send path, the three duplicate-send guards, and all HubSpot and Mailgun logic are untouched throughout.
