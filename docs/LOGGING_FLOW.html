One Run, Three Files

How a request becomes log lines: from uvicorn to campaign_complete, every hop drawn in the order it executes. Color is information — each node is painted by the stream it writes to, and the pink thread is the run_id that joins all three files.

process — what the run did audit — what crossed the boundary & cost system — the service itself run_id — the join key
STEP 1

Boot — uvicorn to a listening agent

Importing service_app runs the module top-to-bottom once; then uvicorn starts the event loop and runs lifespan. Logging is configured first, before anything can fail, so a failure always has somewhere to land. The boot gets its own run_id — that is why startup lines carry a different id than the campaign.

STEP 2

The logger tree — three files on disk, one story on screen

configure_logging() builds one parent and three children. Each child owns a file; all three propagate up to the parent's single console handler. The parent's propagate=False is the wall in both directions: library noise never reaches our files, and our records never reach the root.

STEP 3

Who calls whom — one writer, two shortcuts

Every line in the system goes through _Stream.emit(). Your code either calls it directly on a stream, or uses one of exactly two helpers that call it for you: step() (frames a stage, always process) and hop() (one outbound call, always audit). System has no helper — its events share no shape.

STEP 4

A request arrives — the id is chosen before anything else

run_id = envelope.run_id() or new_run_id() resolves before the guards, so an accepted run and a refused one are findable by the same key. A refusal is a top-level JSON-RPC error — the gateway scores any 2xx without one as a successful dispatch, which is how a refused campaign used to disappear.

STEP 5

The campaign — frames, forks, and the loop that never stops early

The background thread's first act is installing the handle: get_obs(run_id, refresh=True) — the pink thread crossing the thread boundary. From here every borrower (obs or get_obs()) logs under the campaign's id without any threading. Note the list_leads fork: None means the question could not be asked and the campaign refuses to run; [] means nobody matched, which is a success.

THE JOIN
$ grep -hE '"run_id": ?"res-ce6db8faeb46"' logs/research/*.log | jq -s 'sort_by(.ts)'

The value is blanked; the name prints — lqabr-anthropic-api-key is a name, a token count is not a token. That rule holds in every mode, debug included.
