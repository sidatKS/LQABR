C3events.py:68 BOUNCED is a silent alias of FAILED, and it corrupts the precedence map
DefectFAILED = "failed" and BOUNCED = "failed" — identical values, so Python makes BOUNCED an alias, not a member. _PRECEDENCE is written with 8 entries but two of them are the same key, so the literal FAILED: 40 is dead code and FAILED silently inherits BOUNCED's rank of 80.
Proof 
>>> MailgunEvent.BOUNCED is MailgunEvent.FAILED
True
>>> {k.name: v for k, v in _PRECEDENCE.items()}
{'DELIVERED': 10, 'OPENED': 20, 'CLICKED': 30,
 'FAILED': 80, 'STOPPED': 50, 'UNSUBSCRIBED': 60, 'COMPLAINED': 70}
           ↑ source says 40
Two distinct failuresDowngrade: a lead at OPENED gets a transient failed for a retry attempt; FAILED now outranks everything, so the record is written back to FAILED and can never recover — every later delivered/opened/complained returns superseded.
Compliance: unsubscribed and complained also collapse to FAILED, and FAILED is not in ALREADY_SENT_STATUSES — so a recipient who unsubscribed or marked you as spam is eligible to be emailed again on the next trigger.
Now easier to fixThe new email_status enumeration includes BOUNCED as a valid option, so giving it a distinct wire value writes a genuinely distinct status instead of being collapsed. Restore _PRECEDENCE[FAILED] = 40 at the same time, and widen ALREADY_SENT_STATUSES to cover BOUNCED.

Defectresp.json() sits in the else: clause, outside the try, so a JSONDecodeError escapes send_email as something other than MailgunError. send_one's bare except Exception is the only handler that can run after the message was accepted, and it assumes nothing went out.

The prospect has the email. send_one writes FAILED — explicitly commented "FAILED is retryable, so a later campaign works it" — and re-raises. The next campaign sends a second copy. H2mailgun.py:133 One captured webhook signature authenticates forged writes forever
The HMAC is correct and constant-time, and verification is genuinely unbypassable — I checked every path. The gap is what the signature attests to: Mailgun signs timestamp+token only, never event-data. There is no freshness window and no token ledger, so a triple dated 2017 was accepted three times in a row with entirely attacker-chosen event data. The Mailgun signing key is per-account and shared across every webhook on it. Rejecting abs(now − timestamp) > 900 is the load-bearing half and costs nothing.
H3events.py:224 · service_app.py:220 objectId is interpolated into the HubSpot REST path with no validation
It is checked only for emptiness, then handed to get_lead_profile/patch_object, which build f"/crm/v3/objects/contacts/{object_id}". requests normalises dot segments before sending, so ../../../../crm/v3/objects/companies/999 redirects an authenticated GET and PATCH to a different object entirely. validate_writeback checks property names, never object identity. Chained with H2 it is remotely reachable; via H1 it needs no signature at all. The f-string is in shared code, but a ^[0-9]{1,20}$ guard in handle_event and CampaignRequest.resolved_id is entirely ours.
H4outreach.py:318 Only two exception types release the claim; anything else strands the lead permanently
work_lead's try covers MissingLeadContext and SkillError. A UnicodeDecodeError from SKILL.md, an OSError, or anything out of skills.build_context/lead_facts/log_model leaves the lead holding SENT with no email sent — and ALREADY_SENT_STATUSES means no later campaign ever works it. Because load_skills is lru_cached and every lead hits it, one malformed skill file strands the entire batch. Currently masked by C1 — it goes live the moment C1 is fixed, so fix the two together.
H5observability.py:440 An unwritable log directory takes down the container
mkdir and RotatingFileHandler have no error handling. An explicit LQABR_EMAIL_LOG_DIR beats the K_REVISION guard, so pointing it at a read-only path on Cloud Run raises OSError out of the FastAPI lifespan and the revision never becomes healthy. Logging must never be able to fail a run — this is the one place in the subsystem where it can.
H6mailgun.py:110 The retry loop is silent, and its default configuration duplicates sends
mailgun.py imports no logger at all. Nothing records that attempt 1 timed out and attempt 2 was issued — a recipient gets two or three copies and send_email returns success with no trace. The live path passes max_retries=1, which is correct, but the default is 3, so any new caller writing MailgunClient() gets the duplicate-generating configuration. Latent today; the default should be 1.

M1service_app.py:266 The webhook is async but does blocking work
hubspot_campaign is deliberately sync def so FastAPI threadpools it — line 239 explains exactly why. mailgun_events is async def and calls a Secret Manager fetch, HubSpot requests, and two time.sleep(2.0) write-verification pauses. Every event holds the entire event loop for 4+ seconds; a campaign of 200 leads produces a burst that queues the health probe behind it. More urgent now that C2 is fixed — those writes used to fail fast, and will now actually run the full verify-and-sleep path. Changing async def to def is the whole fix; passing verify_after_seconds=0 removes the 4 seconds on top.
