1 · HOW A RUN STARTS — three doors, one pipeline

POST /research/campaign

one post → every lead in its industry

  • body: object_id of the blog Ticket
  • optional industry override, limit
  • synchronous — the caller wants the counts
  • long: drive it from a job, not a 5s webhook

POST /research/run

exactly one lead

  • object_id = the CONTACT
  • summary_ref_id = the BLOG POST
  • different records — mixing them reads the wrong row
  • hand-driven: curl, tests, a re-run of one lead

POST /research/a2a

the Agent Gateway's hand-off

  • A2A JSON-RPC message/send envelope
  • no object_id ⇒ rejected, with the reason
  • acknowledges, then works in the background — the gateway must answer HubSpot inside ~5s

Boot — a mismatch surfaces here, not as a silent no-op

service_app.py · lifespan → ensure_ready()

  • GET /health — model, dry_run, MCP url, tools, search
  • GET /mcp/tools — what the MCP exposes vs what we configured
  • startup check warn logs it · strict refuses to start
  • list_leads is campaign-only, so it shows as missing, not fatal
2 · THE CAMPAIGN — run_campaign(), once per post
STEP 1

Read the post

hubspot.read_blog(object_id) — MCP

  • the Ticket's own record id, exactly what the gateway sends
  • gives blog_summary + blog_industry
  • read once and carried into every lead below
STEP 2

Pick the industry

target.industry or blog.blog_industry

  • a caller override wins — and is logged as an override
  • neither present ⇒ stop: there is nothing to select leads by
STEP 3

Who is in that industry

hubspot_direct.py — the ONE direct call

  • industry lives on the Company, not the Contact
  • companies search → each company's associated contacts → dedup
  • read-only, enforced by a test — no PATCH/PUT/POST-write

“could not ask” ≠ “nobody matched”

  • lookup fails → the campaign does not run at all
  • lookup succeeds with 0 → completed, leads_found=0
  • collapsing these two would report a clean campaign that silently skipped every lead
token ← Secret Manager, never env
3 · PER LEAD — run_research(), once per contact, each independent
STEP 1

Read the lead

get_lead_profile — MCP

  • company, job title, industry, existing context
  • unknown lead ⇒ crm-error, this lead only
STEP 2

Skip gate

skip_if_context_present

  • default false → a re-run overwrites
  • set true to make a campaign resumable without redoing work
  • skipped ≠ failed in the counts
STEP 3

Research

composer → web search + model

  • prompt carries THIS company + the post
  • ~3 searches, ~25 cited sources
  • search failure ⇒ no write, never a fabricated note
STEP 4

Keep only the note

_collect + strip_preamble

  • drops text written before the last search — that is the model narrating its own tool use
  • drops a “Here is the note:” line and its rule
  • guarded: ≥80 chars must survive, else untouched
STEP 5

Write it back

upsert_lead_profile — MCP

  • property lead_context
  • note + cited sources appended
  • status follows the write — a note that could not land is a failure
4 · WHAT COMES BACK

Every failure names its step

nothing is dropped without a reason

inputno object_id / no summary_ref_id
read_leadthe MCP returned no lead for that id
read_blogno blog summary at that record
industrypost carries none and none supplied
list_leadscould not ask HubSpot who is in it
researchsearch or model failed — no write attempted

CampaignResponse

counts first, then the per-lead breakdown

  • leads_found · written · failed · skipped
  • results[] — one row per lead: id, status, chars, error
  • status is completed / partial / failed — “partial” exists so one bad lead never reads as a failed campaign

The write is the next trigger

  • lead_context changes on the Contact
  • → HubSpot contact.propertyChange
  • → Agent Gateway → Email Agent
  • no scheduler, no polling, no queue between the two agents
~3.5–4k chars land, sources included

One lead ≠ the campaign

  • each lead is worked on its own
  • a failure is recorded against that lead
  • the loop carries on
  • one bad record must never cost the others their context

Three streams, one run_id

  • process — the steps: started / ok / failed / skipped / degraded
  • audit — every outbound call: service, endpoint, status, attempt, ms. The credential's name, never its value.
  • system — startup and config
  • one run_id spans the whole campaign, so a post ties to every lead it produced
  • LQABR_RESEARCH_LOG_FORMAT = auto (default) · text · json. auto = readable on a terminal, JSON on Cloud Run — so structured logging is never traded for looks. The log file is always JSON.
