1Emit a routing triggerData source · HubSpot webhook subscription

Four private-app webhook subscriptions on the Contact object fire over HTTPS: Created, decision_maker, lqabr_email_status, lqabr_voice_status. HubSpot performs no value filtering and attaches no agent identifier — the free tier has no custom trigger (D-01).

Emits a JSON array of up to 100 events, each carrying objectId, propertyName, propertyValue, eventId, attemptNumber, changeSource. There is no trigger id in the payload.

Verify the HubSpot v3 signature (added — the ingress is public and can start outreach) · validate the envelope · bound concurrency at 10, HubSpot's throttle. Rejects 401 / 400 / 413 before any routing happens.

3Auditaudit.py

Log run_id + trigger_id for every request, and the routing decision together with the property and value it was based on. Metrics for the HubSpot→agent handoff. Append-only. No lead data.

4Forwarddispatch.py

A2A message/send to the resolved endpoint. Body is the trigger_id and nothing else. HTTPS is converted to agent protocol here. Status, latency and retry count recorded either way.

Orchestrator runtime · Solo.io agentgateway

Sidecar inside this container — one deploy, no hop off-box. Handles HTTP / MCP / A2A and emits access logs, Prometheus metrics and OTel spans. lib/soloai is the Python adapter over it. It is a Rust process, not an importable library — deviation D-02. It cannot decide which agent owns a trigger; that stays in router.py.

A2A message/send · trigger_id only · payload < 1 KB

5Execute the agent taskEmail / Voice / Scheduling agent

Receives a trigger_id and nothing else. Agents are async, independent, and never talk to each other. Performs its channel action, then writes status back to HubSpot — which may itself become the next trigger (email opened → Voice, voice completed → Scheduling).

6Resolve trigger to profileSystem of record · HubSpot CRM

The agent scopes its own request by criteria and receives a chunked lead-profile payload (~5 profiles, bounding agent memory). Full profile data flows here only — never through the gateway. Observability for this hop is recorded agent-side.

2Router decision cascade — Step 2 in detail

Order matters: the cheap rejections come first, and the trigger id is minted only after an event has survived every filter. Every branch is logged with its reason.

route_batch(events) ── for each of ≤ 100 events, in order │ ├─ 1. filter on propertyValue match agents_registry.yaml, first route wins │ ├─ property watched, value is the routing condition → continue │ ├─ property watched, value is not the condition → discard not_routing_condition │ │ the expected case, and the high-volume one: a subscription │ │ fires on EVERY value (D-01). Filtering FIRST is what keeps │ │ this stream out of the dedupe store. │ └─ no route watches this property → discard no_matching_route │ unexpected — someone added a subscription nobody routed │ ├─ 2. de-duplicate attemptNumber > 0 and eventId already dispatched? │ first deliveries are never checked — only redeliveries. │ plus a per-batch set, for the same eventId twice in one array │ yes → discard duplicate_event │ ├─ 3. loop guard mode: self_trigger (default) │ └─ does the owning agent write this property itself? yes → discard self_trigger_loop │ mode: all_api → drops every changeSource=API instead (D-03) │ ├─ 4. mint trigger_id uuid5(namespace, portalId + eventId) → "trg-…" │ deterministic — a redelivery of the same event mints the same id, │ so the audit trail joins and agents can be idempotent. Derived │ from the event's own content when HubSpot sends no eventId. │ └─ 5. resolve endpoint from the agent's endpoint_env ├─ present, enabled, http(s) → RoutingDecision └─ missing / disabled / not a URL → ROUTING ERROR matched but undeliverable — and it carries the trigger_id, so the failure traces by the same id a success would. Never remembered, so HubSpot's redelivery is a real second attempt. Only a hand-off that LANDS is written to the dedupe store. Not discards (they would evict real dispatch records from a bounded LRU — and an evicted record means a second call to a lead already contacted), and not failures (their redelivery must be a real retry).
✔Routed200

Trigger id dispatched to the owning agent. The event id is remembered, so a redelivery de-duplicates and the agent is never woken twice.

◐Discarded200

A normal outcome, not an error. Most events are simply not the value we act on. Logged with a reason and counted; HubSpot must not retry it.

✖Routing error503

Matched but undeliverable, or dispatch failed after retries. Returns 503 so HubSpot redelivers — this is how "a lead is never silently dropped" holds at the HTTP layer.

4Observability — the four streams (FR-7)

Rev 3 makes observability a functional requirement, so it is tested like one. Every record carries run_id and trigger_id, which is what makes one lead's path reconstructible from log search alone.

Token/model is an explicit exclusion, not an omission. The gateway makes no model calls — routing is a config lookup. That fact is written to the system stream once at startup (token_model_stream_not_applicable) so the absence is a recorded decision rather than something a reviewer has to infer.
The trigger-only guarantee is enforced, not promised. Three guards, all tested. The audit writer raises rather than write a record containing any of the nine lead parameters — a log line is the easiest way for profile data to escape a service that swore it carried none. The A2A client raises if anything outside a small allow-list of correlation ids is attached to a dispatch. And because a property value is config-controlled — subscribe to a profile property in the portal and propertyValue arrives holding an email address, under a key FR-7 requires us to log — email- and phone-shaped values are redacted on the way into the log, visibly, rather than raising and taking the ingress down over a portal misconfiguration.
Hardened after an adversarial review. The working version was reviewed line-by-line against the spec before this was called done — 18 findings, 10 of which changed behaviour, each now with a regression test. The two that mattered most: the ingress handler was async def but called blocking I/O, so ten concurrent HubSpot deliveries serialised (30s measured for work that takes 3s, with /healthz starved past the container's own 3s health check); and discards were written to the dedupe store, so the high-volume "not the routing condition" stream evicted real dispatch records from a bounded LRU — a second outreach to a lead already contacted. Both are in the README's full list.

6Deviation register

D-01 is from Rev 3. D-02 and D-03 were found during the build and need sign-off.

D-01No custom trigger on the free tieras designed

HubSpot's free tier cannot filter by value, choose which fields are sent, or set records per trigger. Consequence: value filtering moved into router.py, profile chunking into the agent. Implemented exactly as specified.

D-02"Solo AI" is a process, not an in-process libraryneeds sign-off

Rev 3 describes a co-located orchestration library, imported in-process from lib/soloai, ~500 MB. The product — Solo.io agentgateway, now Linux Foundation — is a Rust data plane: agentgateway -f config.yaml, static YAML, MCP/A2A backends, Prometheus + OTel, UI on :15000. There is no Python library to import.

Built instead: the sidecar runs inside this gateway's own container — one image, one deploy, no hop off-box — and lib/soloai is the Python adapter over it, keeping exactly the module tree Rev 3 specifies. Single ingress, trigger-only payload, HubSpot as system of record and the four streams are all unchanged. Because the business logic depends only on lib/soloai interfaces, swapping in a real library later is a change inside that package alone.

D-03A global "ignore changeSource=API" would disable three of the four routesneeds a decision

Step 2 says to ignore events whose changeSource is an agent write-back (API). Taken literally that removes R1 (the Contact is created by the lead-profile agent via the API), R3 (lqabr_email_status=OPENED is written by the Email agent) and R4 (lqabr_voice_status=COMPLETED is written by the Voice agent) — leaving only a human setting decision_maker. The pipeline would stop after the first hop.

Rev 3 also states the guard's purpose: so the system does not trigger itself. Built: loop_guard.mode: self_trigger — an event is dropped only when the agent owning the matched route is the agent that writes that property (declared per agent as writes: in the registry). That prevents self-triggering without severing the three agent-driven hops. mode: all_api keeps the literal reading one config line away.
